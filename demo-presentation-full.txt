CODE MAP — WHERE THE IMPORTANT FUNCTIONS LIVE

Use this when the panel asks "show me where that is implemented".

THE FIVE THINGS THAT MAKE THIS PROJECT GOOD
-------------------------------------------
1. Double-booking blocked in the DB
   File : supabase/appointments-no-overlap.sql:27
   What : EXCLUDE USING gist (user_id with =, 30-min tstzrange with &&)
   Why  : The app is not trusted to enforce this. Postgres is. A buggy client
          cannot insert a clash. UTC-anchored range explained at lines 22-25.

2. Row Level Security: auth.uid() = user_id on every table
   Files: supabase/patients.sql:21, supabase/appointments.sql:28
   What : Four policies per table (select/insert/update/delete).
   Why  : The insert policy even re-checks the patient FK through patients' own
          RLS (appointments.sql:36) — a trap most tutorials miss.

3. Charts are Postgres views with security_invoker
   Files: supabase/patients_per_month.sql:5, supabase/appointment-status-view.sql:4
   What : Aggregation happens in SQL (generate_series keeps months gapless).
   Why  : Views respect the caller's RLS. No client-side leak, no ORM.

4. Server Actions: one validated mutation path
   File : app/lib/actions.ts
   What : createAppointment (line 40), createPatient (line 224),
          setAppointmentStatus (line 127).
   Why  : Zod parse -> DB write -> revalidatePath -> redirect. Typed
          end-to-end, works without JavaScript.

5. Slot picker with live disabled slots
   File : app/ui/appointments/datetime-picker.tsx
   What : buildTimeSlots (line 27, clinic hours 08:00-17:30 in 30-min slots),
          isBookedSlot (line 76).
   Why  : Taken slots come from the live DB via
          fetchAppointmentSlotTimes (app/lib/supabase-data.ts:112).

Q&A — QUESTION -> WHERE THE ANSWER LIVES
-------------------------------------------
"What stops two bookings at the same time, really?"
  -> The exclusion constraint, not the UI: supabase/appointments-no-overlap.sql:27.
     Red slots are just kindness.

"How is data isolated between clinics?"
  -> RLS at the DB: supabase/appointments.sql:28, supabase/patients.sql:21.
     Automated proof: tests/rls-isolation.spec.ts:4.

"Where does the double-booking error message come from?"
  -> app/lib/actions.ts:67 — Postgres SQLSTATE 23P01 mapped to a human
     sentence (SLOT_CONFLICT_MESSAGE, line 29).

"Is the DB secret exposed to the browser?"
  -> No. All reads/writes go through Server Components/Actions; the Supabase
     server client lives in utils/supabase/server (cookie session). Charts
     fetch server-side and pass plain props.

"How does the chart update without a page refresh?"
  -> revalidatePath('/dashboard') after every mutation: app/lib/actions.ts:72,
     108, 142, 254.

"Why not an ORM or raw SQL in an API route?"
  -> Views aggregate in-database with security_invoker and RLS still applies:
     supabase/patients_per_month.sql:5. Fewer round-trips, no duplicated auth.

"What breaks if Supabase is down?"
  -> Errors funnel through AppError/handleError (app/lib/errors.ts) and render
     via app/dashboard/error.tsx. Surfaced, not swallowed.


HONEST LIMITATIONS (have these ready, unprompted)
-------------------------------------------
1. Single clinic timezone — app/lib/time.ts:2 hardcodes +02:00 /
   Africa/Johannesburg; fromDateTimeLocal and formatSA assume it everywhere.
2. Manual status tracking — Done/No-show set by staff
   (setAppointmentStatus, app/lib/actions.ts:127). Nothing reminds the
   patient. Charts are fixed windows (last 6 months / this month).
